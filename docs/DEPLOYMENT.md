Status: PARTIALLY IMPLEMENTED (Phase 3, migrations through Phase 4 PR 4.3)

- IMPLEMENTED: local development and CI, which are reproducible without any
  hosted service; the Supabase CLI project structure (`supabase/`); a build
  guard in `apps/web` for deployments.
- PLANNED — owner action: the hosted Supabase DEV project and the Vercel
  project. Both are dashboard steps listed below. No credentials, project
  refs or domains are in this repository, and none may be added.
- BLOCKED — owner decision: a production host for `apps/api` and
  `apps/worker` (ADR-012 is still open). Until it is decided, a deployed web

# Local development

The default path needs no Supabase account:

```sh
docker compose up -d            # PostgreSQL 16 and Redis 7
cp .env.example .env
pnpm install
pnpm run db:deploy              # apply packages/database/prisma/migrations
pnpm --filter @eternal-forge/web run auth:stub &   # Supabase Auth test double
pnpm dev
```

## Optional: the full local Supabase stack

`supabase/config.toml` was generated by `supabase init` (CLI 2.117.0). It is
configured for this repository:

- Migrations and seeds of the CLI are **disabled**. Prisma owns the schema
  (ADR-011), so there is exactly one migration history.
- Auth redirects allow `http://localhost:3000` and `http://127.0.0.1:3000`.
- Realtime, Edge Functions and Analytics are disabled. Nothing uses them.

```sh
npx supabase@2.117.0 start      # needs Docker; prints local URLs and keys
# Local keys are generated by the CLI and printed by `supabase status`.
# Put them in .env (never commit it):
#   DATABASE_URL / DIRECT_URL  = the printed "DB URL" (port 54322)
#   SUPABASE_URL               = the printed "API URL" (port 54321)
#   NEXT_PUBLIC_SUPABASE_URL   = the same API URL
#   NEXT_PUBLIC_SUPABASE_ANON_KEY = the printed anon / publishable key
pnpm run db:deploy
```

Do not run the `auth:stub` test double at the same time. Its port, 54329, is
also the CLI's default pooler port, although the pooler is disabled here.

# Required variables

| Variable                        | Used by            | Browser? | Notes                                                          |
| ------------------------------- | ------------------ | -------- | -------------------------------------------------------------- |
| `DATABASE_URL`                  | api, worker        | **never** | Runtime connection. See "Supabase DEV" for which one.        |
| `DIRECT_URL`                    | Prisma Migrate     | **never** | Direct connection for DDL (ADR-011).                          |
| `REDIS_URL`                     | api, worker        | **never** |                                                                |
| `SUPABASE_URL`                  | api                | **never** | `https://<project-ref>.supabase.co`; issuer and signing keys. |
| `AUTH_JWT_AUDIENCE`             | api                | **never** | Defaults to `authenticated`.                                  |
| `SUPABASE_JWT_SECRET`           | api                | **never** | Only for projects still on legacy HS256 signing (ADR-016).   |
| `API_CORS_ORIGINS`              | api                | **never** | Exact web origins; no wildcard.                               |
| `NEXT_PUBLIC_API_URL`           | web (build time)   | yes      | Public URL of the API.                                         |
| `NEXT_PUBLIC_SUPABASE_URL`      | web (build time)   | yes      | Same project URL.                                              |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | web (build time)   | yes      | The anon / publishable key. Designed to be public.            |

**Server-only, always:** the `service_role` key, any Supabase secret key
(`sb_secret_…`), the JWT secret and every database URL. No Phase 3 process
needs the service-role key at all. None of these may ever appear under a
`NEXT_PUBLIC_` name. Two checks enforce it:

- `apps/web/next.config.ts` refuses to build when a `NEXT_PUBLIC_` variable
  has a privileged-looking name (`SERVICE_ROLE`, `SECRET`, `JWT`, database
  URLs and so on). On Vercel (`VERCEL=1`) it also refuses to build when a
  required public variable is missing. Without that check the app would
  silently fall back to `localhost`.
- CI builds the web application with a canary service-role key present, then
  fails if the value or the names of privileged variables appear in
  `.next/static`.

# Supabase DEV — owner checklist

The workflow is always: **local development → migration → tests → Git (PR,
green CI, merge) → Supabase DEV.** Nothing is ever changed in a hosted database
by hand.

1. **Create the project** in the Supabase dashboard (name, region, database
   password). Store the password in a password manager, not in the
   repository.
2. **Signing keys.** Prefer asymmetric JWT signing keys (Project Settings →
   JWT Keys). The API then verifies tokens through the public JWKS and needs no
   secret. With legacy HS256 only, set `SUPABASE_JWT_SECRET` on the API host.
3. **Auth settings** (Authentication → URL Configuration):
   - Site URL: the production web origin, once it exists.
   - Redirect URLs: `http://localhost:3000/**`, the Vercel production domain,
     and a Vercel preview pattern for your team, for example
     `https://*-<team-slug>.vercel.app/**`.
   - Email confirmation: the web app supports both settings. With
     confirmation on, sign-up shows "check your email" (ADR-016).
4. **Link the CLI** (optional, for inspection only):
   `npx supabase@2.117.0 link --project-ref <project-ref>`. The ref and
   password are prompted for; nothing is written to the repository.
5. **Apply migrations** from a clean checkout of `main`:

   ```sh
   DIRECT_URL='<direct or session-pooler connection string>' pnpm run db:deploy
   DIRECT_URL='…' pnpm --filter @eternal-forge/database exec \
     prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code
   ```

   The second command must print "No difference detected". Use the direct
   connection (`db.<project-ref>.supabase.co:5432`) or the Supavisor
   session-mode pooler. The transaction pooler (port 6543) cannot run DDL.

6. **Verify the security posture** in the SQL editor:

   ```sql
   SELECT relname, relrowsecurity FROM pg_class
    WHERE relname IN ('profiles', 'characters', 'combat_runs', 'offline_runs'); -- all true
   SELECT has_table_privilege('anon', 'combat_runs', 'SELECT'),
          has_table_privilege('authenticated', 'characters', 'UPDATE'); -- false, false
   ```

   The migrations revoke `anon` and `authenticated` on every game table, and
   RLS denies them by default (docs/SECURITY.md — "Supabase").

7. **Runtime connection for the API.** Use the direct connection or the
   Supavisor **session** pooler. The API is a long-lived process with its own
   pool (ADR-012). The transaction pooler has not been validated with the
   Prisma `pg` adapter in this repository. Validate it before using it.

# Vercel — owner checklist (apps/web)

`apps/web/vercel.json` holds the build settings and no secrets.

1. **Import** the GitHub repository in Vercel.
2. **Root Directory:** `apps/web`. Framework: Next.js. `vercel.json` already
   sets install (`pnpm install --frozen-lockfile`) and build (Turborepo,
   filtered to `@eternal-forge/web` and its workspace dependencies).
3. **Production environment variables:** `NEXT_PUBLIC_API_URL`,
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Nothing else.
   The build fails if one is missing or if a privileged key is exposed.
4. **Preview environment variables:** the same three, pointing at the DEV
   Supabase project and a DEV API.
5. **API URL:** requires the API host decision (below).
6. **Supabase public URL and key:** from Project Settings → API.
7. **Auth redirect URLs:** add the Vercel production domain and preview
   pattern to Supabase (step 3 above). Add the same origins to the API's
   `API_CORS_ORIGINS`. It takes exact origins, so a preview deployment works
   against the API only when its origin is listed.
8. **Deploy a preview.**
9. **Smoke test** the preview: `/api/health` returns 200. `/status` reports
   the API. Register, name a hero, fight once, reload, and check that the
   stage and gold persisted.
10. **Promote** to production only after the smoke test passes.

# What blocks a playable deployment

ADR-012 left the host for `apps/api` and `apps/worker` open, and it is still
open. Phase 3 does not decide it. The web application can be deployed to
Vercel today, but it cannot play: every gameplay request goes to the API
(ADR-003), which has no hosted home yet. `/status` reports the API as
unreachable, which is accurate.

**Owner decision required:** a container or always-on host for the NestJS API
(and later the worker), with a pooled PostgreSQL connection, `SIGTERM`
draining and `/health`/`/health/ready` probes. Record it in an ADR that
supersedes ADR-012's open part. The Vercel checklist above is then completed
with the API's URL and CORS origins.

# Migration deployment order (every PR with a migration)

Application code that expects a new column must never reach an environment
before its migration. After merging a PR that adds a migration:

1. Run the GitHub Action **Deploy Supabase DEV**
   (`.github/workflows/deploy-supabase-dev.yml`) from `main`.
2. Check that it reports no drift.
3. Only then deploy or restart the API against Supabase DEV.

Phase 4 PR 4.3 adds `20260923180000_offline_progression`
(`characters.offline_seed`, `offline_runs`). It is additive: existing rows get
an offline seed, nothing else changes, and the previous API version keeps
working against the migrated schema. The new API version fails on every
character read without it.

**AFTER MERGE: RUN "Deploy Supabase DEV" BEFORE VALIDATING THE NEW ITEM API AGAINST DEV.** Wait for migration `20260924120000_inventory_equipment_persistence` and drift verification to succeed before deploying/restarting the API. The migration is additive, but new item endpoints require both new tables.

**AFTER MERGE: RUN "Deploy Supabase DEV" BEFORE VALIDATING THE NEW APPLICATION CODE AGAINST DEV.** Wait for migration `20260924180000_combat_item_drops` and schema-drift verification to succeed before deploying/restarting the API. The migration is additive and portable to plain PostgreSQL 16; it adds one nullable reward association, unique index and foreign key.
